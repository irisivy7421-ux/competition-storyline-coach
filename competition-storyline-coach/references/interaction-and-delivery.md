# 访谈界面与交付模板

在第一次提问前和最终交付前读取本文件。目标是让用户看得见投入、进度和最终成果，同时保持每轮问题轻量。

## 开场卡

第一次提问前，用以下结构说明本次合作：

```markdown
## 本次将共同完成

**预计投入**：5–7个主问题，约10–15分钟  
**最终交付**：聊天内方案摘要 + 飞书文档完整版  
**可随时结束**：回复“先总结”，即按现有信息交付并标出缺口

问题定位 ○ → 现有缺口 ○ → 方案机制 ○ → 验证落地 ○
`░░░░░░░░░░ 0%｜第 1/7 问｜预计还需 10–15 分钟`
```

不要求用户先选择模式。默认按标准访谈推进；只有用户明确希望深入时，才扩展到8–10个主问题，并更新预计题数和时间。

## 每轮提问卡

每个主问题使用同一结构：

```markdown
## 方案梳理进度

问题定位 ✓ → 现有缺口 ✓ → 方案机制 ● → 验证落地 ○

`███████░░░ 70%｜第 5/7 问｜预计还需 3–5 分钟`

**刚刚确认**  
AI把偶发的表达机会，变成随时可进入的个性化练习场景。

**这一问要解决**  
确认产品效果如何被真实行为证明。

### 问题

如果让30名学生试用4周，什么变化最能证明产品有效？
```

格式约束：

- 阶段轨道始终保持同一顺序，用 `✓` 表示完成、`●` 表示当前、`○` 表示未开始。
- 进度条使用10格文本条；百分比按关键信息完成度估算，不按问题数量机械计算。
- 同时显示题号和预计剩余时间；若预计总题数变化，简短说明原因。
- “刚刚确认”和“这一问要解决”各不超过两行。
- 一次只出现一个主问题。
- 只有用户表示不知道或卡住时，才追加2–4个回忆方向；不要提前给选项诱导答案。
- 不在每轮重复完整评分表、历史结论或长篇方法说明。

## 聊天摘要模板

最终回复必须有足够信息量，让用户不打开文档也能理解结论。建议控制在约600–1200个汉字，复杂方案可适度增加：

```markdown
## 方案结论

**产品名称与一句话定义**

用一段话说明目标用户、关键问题和产品如何改变行为。

**核心机制**

`输入 → 行动 → 反馈 → 再输入 → 更高难度场景`

简述AI的关键作用、用户成长路径和企业价值。

**验证与风险**

列出最小试点、关键指标，以及最需要验证的1–3项假设。

**完整方案**

[查看飞书文档：文档标题](飞书文档链接)
```

不得只写“已完成，请查看链接”。聊天摘要与飞书文档分别承担即时理解和长期协作的作用。

## 飞书文档交付

使用可用的飞书文档工具新建一份文档，默认标题：

`《{企业或赛题名称}创新方案与比赛故事线 V1》`

默认目录：

1. 项目摘要
2. 比赛命题与评分规则
3. 目标用户与真实问题
4. 现有做法与关键缺口
5. 产品概念与核心体验
6. AI工作机制
7. 用户成长路径
8. 企业价值与推广逻辑
9. 最小试点与验证指标
10. 风险、假设与待验证项
11. 比赛演讲故事线
12. 评分覆盖矩阵
13. 演讲时间分配
14. 访谈洞察记录

文档使用三种显式标签：

- **已确认**：来自用户材料、正式规则或可核验来源。
- **方案判断**：由当前访谈和推理形成的设计结论。
- **待验证**：缺少真实用户、数据、来源或主办方确认。

交付规则：

- 将完整内容写入文档后再提供链接，不能创建空文档或仅放摘要。
- 默认新建文档，不覆盖用户已有文档；用户明确提供目标文档并要求更新时除外。
- 保留评分规则原意；权重冲突或总和异常必须在文档中显式标注。
- 不编造学生访谈、产品效果、收入或推广数据。
- 若飞书文档能力不可用、认证失效或权限不足，先在对话中交付完整内容并说明具体阻断；不得伪造链接或宣称文档已创建。
